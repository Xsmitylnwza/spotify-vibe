## 5. State, saving and side-effect ownership

### 5.1 Selection semantics

| Input / action | Required result |
| --- | --- |
| Manual pin in app mode | Selected saved Scene wins for one hour; expiry and cancellation visible; existing contract retained |
| Scheduled override in legacy mode | Selected saved Scene wins until the next enabled slot; no-slot precondition explained |
| Auto in app mode | Preserve current running-app selection: most recently foregrounded enabled mapped executable among running processes; eligible running fallback; an unmapped foreground window alone does not clear a still-running mapped Scene |
| No eligible running mapped app | Clear in Auto; distinguish this verified empty state from scanner error/staleness |
| Auto in legacy schedule mode | Select current local-time slot; enabled slots wrap across midnight; deleting/disabling the final slot clears automatic output and pauses selection with explicit state |
| Pause Auto | End automatic changes after the bounded RPC handoff below, then hold the resulting acknowledged activity. Current backend ends the override selection when pausing; show this explicitly. Do not select another Scene during hold |
| Hide / Clear | Persist pause/no-override and remove this companion's activity; no queued apply may restore it |
| Resume Auto | Recompute from current app/time data, not cached stale desired state; do not fabricate a match when detection is unknown |
| Edit/save the Live Scene | In Auto/pin preserve the current automatic refresh contract and label it; a failed save cannot refresh Discord. During Pause the held payload is immutable: edits save locally and require explicit Show/Resume to replace it |
| Quit | Prepare every registered Studio draft as saved or explicitly discarded; then stop work, drain writes/owned activity/helpers/listener and close the host; failed preparation cancels exit |

Do not change app-selection priority to foreground-only, reintroduce schedule-first onboarding, or introduce permanent pins under the label of a cleanup.

Legacy DST policy uses dated local boundary instances for both active and next selection. A nonexistent start is normalized forward by the timezone's gap (`02:30` → `03:30` for a one-hour gap); an ambiguous repeated start fires once at its first occurrence that day. This matches JavaScript Date boundary construction while fixing the separate wall-minute active calculation. Timezone/clock changes recompute the latest valid instance; no replay of missed transitions. Test the policy before changing the pure scheduler.

Detection freshness defaults: mark running observations stale after 5 seconds without a healthy snapshot; retry helper failure with capped 1/2/4/8/16/30-second backoff. In Auto hold the last acknowledged activity for up to 30 seconds of unknown detection, then clear with a detection-error reason; never pretend all apps closed. Pause continues its intentional hold behavior. Installed catalog retains last-good on failure with scan age/error, but a successful empty scan replaces the cache; refresh is single-flight and returns a pending receipt instead of blocking for a 120-second scan.

Pause has an explicit external-effect barrier. After its paused preference is committed, invalidate all automatic applies not yet submitted, show **Pausing**, and wait at most 8 seconds for the one already-submitted RPC to settle. A successful submitted RPC is recorded as an external effect even if its old selection generation is stale; capture that resulting immutable acknowledged payload/source/start timestamp as `heldActivity`, then acknowledge Pause. This allows the already-submitted activity to finish before Pause takes effect; copy must not promise cancellation of a sent request. The actor owns this handoff, so ignoring old completion metadata alone is insufficient.

If that RPC fails/times out, fence the connection generation, stop automatic submissions and report **Paused — output uncertain/disconnected**, not successful hold. Keep the last known acknowledged payload as a restoration candidate; reconnect explicitly restores that candidate and updates acknowledgement only after RPC success. When no acknowledged activity existed, Pause holds nothing. In the same process a healthy reconnect restores the captured payload instead of recomputing an app/slot; save/delete of its originating Scene does not mutate the captured payload. Explicit Show or Resume replaces the hold. Hide/Clear discards both held/restoration candidates and completes an explicit clear barrier after any submitted RPC; it cannot depend solely on a previously false `active` flag.

Cold restart preserves paused preference but deliberately starts with no owned activity and no persisted hold payload. The UI says **Auto paused — nothing published since restart**. A held payload is process-local, unlike a persisted Manual Override. The live/app/time snapshot and last acknowledged payload are separate, and Pause/Hide results become certain only after the appropriate actor barrier. W3 tests record actual RPC submissions/effects as well as the returned state.

### 5.2 Committed state and revision

One application-level command queue owns committed config. Each command reads the latest committed revision inside that queue, validates a candidate, awaits durable save, then publishes `{config, revision}` and requests reconciliation. Disk write serialization alone does not protect the application's read/modify/write state.

Config writes require an expected revision. Two tabs editing the same revision: the first commit succeeds; the second returns a structured 409 conflict with the latest revision and a recovery choice. Never auto-overwrite or auto-merge conflicting Scene text. The UI retains its draft and offers Reload latest or copy/reapply edits. A revision derives from persisted state and must change across commits/restarts; do not reset it to a constant on boot. All UI mutation calls, including mapping, mode, pin, pause, clear and Codex session updates, use the same centralized client contract.

Maintain separate renderer `draftGeneration`, last acknowledged generation and pending save. Capture payloads from a draft independent of server config. A completed save can update the base revision and runtime; it cannot overwrite fields edited after capture or label a newer draft saved. Serialize local mutations and handle 409 with the same recovery path. New Scene creation must commit before mapping it; dependency-aware delete includes expected revision and the explicitly confirmed references in one transaction. Mapping saves preserve mode/pause/pin; Enable Auto is a separate deliberate command. Pagehide keepalive remains best effort; it must not bypass revision or be described as guaranteed persistence.

### 5.3 Observable result

Successful storage and Discord application are distinct stages: `saved`, `selected`, `rpcApplied` or `pendingReconnect`, plus the returned committed revision. `ok` is not a claim that Discord viewers see the card. Snapshot includes desired Scene/source and last successful applied Scene/source/time separately; a failed apply retains evidence of the previous result and exposes retry status. Store/disconnect/apply errors never discard the local draft.

Reconciliation has a latest desired generation. Check freshness immediately before RPC submission and when handling completion; serializing the RPC queue alone is insufficient. Clear/Pause/Quit invalidate pending applies. A late completion must not overwrite a newer desired/applied snapshot. A dead scanner is unknown/error and must not synthesize an empty running set. Restart/reconnect recomputes current selection and does not reset an unchanged activity timestamp unnecessarily.

### 5.4 Controlled exit and renderer drafts

Renderer Quit, tray Quit, preventable OS/app quit and update installation first enter one idempotent **prepare-exit** request with a 10-second total preparation deadline. Runtime owns participant/receipt coordination for registered Studio clients through a protected control connection; UX owns each client's freeze/capture/save response; lifecycle admits shutdown/install only after that receipt. Include all registered editing clients, so a second or hidden tab is not skipped merely because the initiating window is clean. The control connection can receive exit preparation while normal hidden-page UI polling is suspended; it uses the same token/origin boundary and contains no keys.

UX stops debounce/new edits, captures the latest Scene draft generation, awaits any older submitted mutation, then commits that captured generation with the current expected revision. Preparation acknowledges the committed revision/generation, not queue emptiness. Invalid input, 409, failed/uncertain save or unreachable client cancels controlled exit by default and keeps the host/draft alive with visible recovery. Offer keep editing, copy Scene edits or explicit discard of the identified uncommitted edits; timeout alone never authorizes discard. Settings/key forms requiring explicit Save are not silently committed by exit preparation. A client never registered/no editing renderer is distinct from a previously registered client whose draft state is unknown.

Only after all participants are saved or their specific discard is explicitly confirmed does lifecycle stop helpers/admission, drain accepted storage and the RPC stop barrier, release leases, and quit/install. Repeated actions share the same request; cancellation restores editor operation. Missing-renderer uncertainty needs an explicit force/discard choice through a trusted host recovery surface; there is no automatic update restart through it. Browser tab loss, forced OS termination and power failure retain the stated best-effort limit; pagehide is not a controlled-exit receipt. W4/W6 tests assert persisted bytes and process/install admission through debounce-pending, later typing, invalid/409/failed saves, hidden/second/missing clients, timeout/cancellation/discard and update restart.

## 6. Security, persistence and lifecycle contract

### Local request and renderer boundary

Bind loopback only. Parse the request inside the error boundary and validate `Host` against the exact configured loopback authority before reading or mutating data; reject an absolute target pointing elsewhere. Browser requests require the canonical Studio Origin; deny foreign/null origins for mutations. Protect every mutation with an unpredictable per-process token obtained from the same-origin bootstrap, not query strings or logs. Origin-less local automation must supply that token. Maintain JSON Content-Type, supported-method and a **1 MiB (1,048,576-byte) JSON body ceiling**, with a 5-second total body-read deadline; accumulate buffers before a single strict UTF-8 decode so chunk boundaries cannot corrupt Thai/emoji. Reject null/array/scalar bodies where an object is required. No simple form request can quit or change settings. GET never mutates config/preferences/Presence; installed-app refresh becomes an explicit protected command. GIF retrieval consumes provider resources and therefore requires the same token/trust checks before using the configured key.

The byte ceiling preserves accepted serialized data rather than copying the baseline's character count: `studio-server.mjs:502` limits a decoded JavaScript string to 262,144 UTF-16 units; valid UTF-8 for that text requires at most 786,432 bytes, with room under 1 MiB for the revision envelope. Keep existing schema/field constraints, including 20 Scenes, 24 slots and 100 mappings with 1,024-character executable paths. W0/W1 fixtures cover maximum supported counts, Thai/emoji, JSON escaping, longest accepted fields and revision metadata through the actual guarded reader, including config and mapping routes. A coordinator pure validator fixture with all three maximum counts measured 625,598 bytes for full config and 334,239 for mappings, both fitting this ceiling. These fixtures are compatibility evidence, not a live HTTP proof. If a future protocol needs a lower per-route limit, demonstrate all supported serialized requests still fit before changing it. Over-limit/timeout/invalid UTF-8 is typed rejection with zero effects and a retained renderer draft; never truncate existing data to fit.

Studio is a top-level document only. W1 sends `Content-Security-Policy: frame-ancestors 'none'` as an HTTP response header on every Studio document response, plus `X-Frame-Options: DENY`; a meta policy is insufficient. This rule also covers boot/error documents and the CLI browser surface, independently of Electron's main-frame IPC checks. G5 verifies a foreign-parent frame cannot render an interactive Studio or trigger a command, while direct owned navigation works. This policy is decided here; its browser-specific proof remains external.

This protects browser-origin boundaries, not an already compromised local OS account. Do not add cloud identity, accounts or long-lived network authentication. Token rotation follows process restart; the client refreshes a stale token without replaying side effects blindly.

Electron accepts navigation and IPC only from its owned canonical Studio document/main frame. Deny untrusted top-level navigation/popups; supported external HTTPS links open through a validated system-browser handoff. Block javascript/file/data and unexpected URL schemes. Use context isolation and sandbox the existing minimal preload where supported; verify actual packaged preload loading before acceptance. Introduce a CSP matching the two current inline scripts through nonces or their extraction, validated image domains and intentionally chosen font handling; avoid breaking arbitrary owner HTTPS artwork without a documented policy.

On occupied port Electron must not load the other listener into its privileged window. Fail with a typed error and recovery. CLI's advertised reopen-existing behavior can remain only after positive identification of the same companion; preserve it through a small tested ownership handshake, otherwise report conflict explicitly. App/installation identity is not a substitute for security proof if a listener is untrusted.

### GIF provider admission and cancellation

Security owns provider admission/cache/cancellation; runtime wires HTTP disconnect and shutdown signals; UX owns the bounded picker above. Keep existing query/limit/offset validation and completed-cache TTL/entry bounds. Coalesce identical normalized query/limit/offset requests within the same credential generation. Per companion, allow at most **2 active provider requests, 8 queued distinct searches and 32 attached HTTP requesters total**; excess receives typed 429/busy with Retry-After, without starting upstream work. The admitted request has a 10-second total queue/transport deadline. Each requester detaches on abort/disconnect; only the last detachment removes queued work or aborts a shared fetch. Disconnect one client must not cancel another client's identical search.

Provider response bytes are capped at 2 MiB and normalization retains no more than the validated result limit. Cancellation, timeout, provider error/429 and malformed responses release waiters and queue ownership in `finally`; an active slot stays occupied until its transport settles/closes, so cancelling metadata cannot admit work beyond the real concurrency cap. Failed/cancelled results are not cached. Credential replacement fences old results and aborts obsolete work; keys/queries are not added to diagnostics. Shutdown stops admission and aborts/drains active work. There is no automatic unbounded provider retry. A non-settling transport leaves bounded work unavailable with visible Retry rather than opening more requests.

W1 fixtures use deferred fake transports that expose starts, aborts and actual settlements: identical and distinct queries, several clients, one-versus-last cancellation, queue overflow, timeout, ignored abort, key replacement, provider 429, oversized response and shutdown. Assert actual upstream concurrency and retained requester counts, not only which response the renderer displays. W4 exercises enough page appends/window replacements to assert the 48-node cap, bounded metadata, focus and selected-art preservation. G6 measures these chosen bounds; it does not choose the policy later.

### Durable storage and data-preserving recovery

Updated cooperating processes have one owner for every canonical config/secrets file identity, independent of port or Electron's instance lock. A supported upgrade must first satisfy the legacy-writer handoff below; a new lease cannot restrain a predecessor that never checks it. Acquire shared per-file leases in deterministic path order **before** reading/creating/migrating/recovering either file; the canonical identity resolves existing real paths/parents and Windows case aliases. Reject overlapping identities and reject a second updated writer even on a different port. After legacy admission, startup acquires leases, reserves the requested loopback port with a guarded booting response, then loads storage; bind failure releases leases without migration/default writes. Future/read-error mode may serve diagnostics from the owned server but performs no config/secret/RPC/startup mutation.

The small shared primitive uses exclusive creation with owner PID/process-incarnation metadata and a random ownership nonce. The owner retains the lease through config/secret drain and helper/RPC/server shutdown; release removes only a matching nonce. Never reclaim by age/port absence alone. Confirm owner process exit before stale-lease recovery; unverifiable or reused-PID cases fail read-only with an actionable recovery path and preserved bytes. G2 verifies canonical aliases, two processes, crash/restart and Windows liveness/ACL details; the ownership rule is decided here, not deferred to that experiment.

Runtime owns the shared lease primitive and server acquisition/release. Security owns `setup-giphy-key.mjs`/secret-writer integration. The standalone key helper acquires the same secret-file lease and refuses while a companion owns it, directing the owner to Settings or to stop the companion; it does not bypass ownership via a fresh local queue. Secret writes under the companion require its held lease. Different profiles with disjoint storage can still operate independently. Protect custom config/secrets paths individually, not merely a hash of the combined pair, so partially overlapping profiles cannot race.

Keep the current config/secrets separation and field validators. Save candidate bytes to a unique temporary file; replacement failure leaves the prior durable file intact. Do not unlink the destination merely because rename returned EPERM. Serialize secrets read/merge/write, including independent partial updates, and preserve an unrelated key. No plaintext key appears in config/runtime, logs or review fixtures; `mode: 0600` alone is not a verified Windows ACL guarantee.

ENOENT permits default creation. Read/permission errors preserve files and enter recoverable error mode. Malformed content can be replaced only after a verified backup; unsupported future schema cannot be normalized into v2 and overwritten. Recovery never reports that a backup exists unless it can read that backup. Prefer existing primitives and a backup/replace protocol over adding a database. Test injected read, backup, rename and crash failures with real temporary files and controlled filesystem seams; confirm Windows sharing/ACL behavior separately.

### Legacy-writer upgrade handoff

W0 explicitly supports the reviewed 1.0.7 predecessor, including CLI companions on different ports and its standalone key helper; other predecessor versions require a verified compatibility fixture before exposure. First shared-profile activation is a quiescent cutover: lifecycle identifies supported legacy installation/process/startup entry points, retires their automatic relaunch paths while preserving the explicit startup preference, stops only positively identified owned writers, and confirms their process incarnations exited. If ownership/overlap/exit cannot be established, refuse shared-storage activation before reading/backing up/migrating that profile; offer close-older-companion/retry or an explicitly disjoint disposable test profile. Do not terminate an unidentified listener/process or infer exit from port absence.

After that handoff, runtime acquires the new per-file leases, reserves its owned port, takes and verifies config/secrets backups, then loads/migrates and enables the new host startup provider only according to the retained preference. Lifecycle records the predecessor/profile, verified exits, retired launch paths and backup provenance without secrets. An updated helper uses the new lease protocol; obsolete manual helpers/CLI binaries are retired for this profile. Restarting a noncooperating old binary against it after cutover is unsupported and cannot be claimed safe merely because a lease exists. Unknown or changed external storage interrupts mutation with an explicit recovery error; it is not silently merged over the committed state. The same quiescent rule applies to backout before restoring a compatible copy and re-enabling one predecessor launcher.

Runtime owns admission and storage boundaries; lifecycle owns predecessor/process/startup handoff. Then prove confirmed exit, one updated writer, a verified backup and compatible backout; retain opted-out startup. ### Desktop lifecycle

One host-specific startup provider owns read/write/reporting: CLI uses the existing VBS mechanism; packaged Electron uses native login items. Electron must not invoke the legacy launcher with `process.execPath` pointing to the packaged app and a Node script inside ASAR. Preserve explicit existing preferences and detect/remove obsolete launcher only after the new startup path is verified. An app upgrade must not silently reverse a previous opt-out.

Runtime resolves an immutable nonsecret **profile descriptor** at boot: canonical config/secrets paths, data directory, host mode, port and the applicable startup directory. Lifecycle persists the selected descriptor atomically in private host metadata and binds launcher/login/update restart to its stable pointer; transient parent environment is not the restart contract. Include no key values in the descriptor, launcher argv or receipts. Re-resolve/validate the descriptor's identities before lease acquisition and storage load; missing, corrupt, unsupported or mismatched descriptors fail with typed recovery and zero default-profile creation/Presence, rather than falling back silently.

One startup registration binds one selected profile; a different running profile cannot silently replace it. Custom/split-directory/space/Thai paths are supported by the same descriptor contract. Installation/update must retain its pointer and verify the restarted process's resolved identities. Backout translates the descriptor into the supported predecessor's explicit launch environment/arguments before starting it; an incompatible host/predecessor profile combination refuses automatic restart with a preserved-data recovery path. Opt-out and the chosen profile survive together. Runtime owns descriptor/resolution; lifecycle owns durable pointer and launcher/update/backout consumption; standalone key setup uses the same selected-profile resolver. G2/G4 use a default-profile sentinel and require zero writes there while a custom profile is resumed.

Tray creation failure cannot make the app unreachable: keep/show the window and provide ordinary Quit. Route renderer Quit, tray Quit, OS quit and updater restart through one idempotent shutdown path. Stop helpers, queue and RPC before exit; repeated stop is harmless. A typed startup/port/server error must settle startup and clean resources. Update notification uses void-return-safe send, guarded windows and explicit checking/download/error stages; no unhandled promise or event callback may crash the companion. Validate correct release metadata/artifact pairing and signer policy before updater exposure. Windows is the acceptance platform; macOS/Linux targets remain unproven until host-specific validation.

Lifecycle owns the `extraResources` layout; runtime owns a shared dev/packaged resolver and both helper consumers, with the trusted Electron host injecting the real resource root. CLI/dev keeps real repository-relative files; external processes never receive an `app.asar` virtual path. G4 must start both packaged helpers and read the approved icon through their actual filesystem/argv, including paths with spaces; file-list/source-string checks alone do not pass.
