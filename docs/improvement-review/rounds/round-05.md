## Independent findings

### R5-M1 — Major: controlled exit does not settle renderer drafts before host shutdown

- Consequence: an acknowledged server-write drain can finish while a valid edit is still inside the 650 ms renderer debounce, or while newer typing follows an older submitted save; Quit/update can then destroy the only copy. Invalid/conflicting drafts have the same missing decision boundary.
- Trace: input → UX draft owner (`scripts/discord-presence-studio.html:3094-3112`) → delayed save (`:2832-2839`) → renderer Quit (`:3291-3309`) or install action (`:3750-3752`, `electron/preload.cjs:13`) → lifecycle stop/install (`electron/main.js:259-283`, `scripts/studio-server.mjs:671-687`) → window destruction. Recovery is only best-effort pagehide (`scripts/discord-presence-studio.html:2846-2860`), which SPEC:122 explicitly declines to guarantee.
- Evidence of plan gap: SPEC:67, 74, 102, 122, 126, 178 promises draft integrity and durable-operation drain but defines no renderer-to-host shutdown preparation/acknowledgement; WF:54-56 splits the participating owners without this seam. Draining already accepted writes does not submit an unsent draft.
- Minimal correction: UX owns a controlled-exit preparation that freezes/captures the latest generation and awaits its committed revision before shutdown admission; invalid/409/write failure cancels controlled exit unless the owner explicitly chooses to discard/copy edits. Lifecycle routes renderer/tray Quit and update restart through that preparation with a bounded unreachable-renderer outcome; unpreventable OS termination remains explicitly best effort. Test debounce-pending, later typing, invalid draft, 409, failed save and missing renderer across Quit/install; do not rely on pagehide or server queue emptiness.

### R5-M2 — Major: startup/update/backout does not bind relaunch to the admitted storage profile

- Consequence: a companion started with custom config/secrets paths can restart at login/update against the default profile, create defaults and publish a different Scene even though leases, opt-out and the one-launcher count all pass.
- Trace: CLI/Electron entry → profile resolution from `PRESENCE_CONFIG_PATH` / `PRESENCE_SECRETS_PATH` (`scripts/studio-server.mjs:55-62`) → startup adapter (`:85-91`, `:163-170`) → VBS captures executable/script/client ID/port only (`scripts/windows-autostart.mjs:24-35`) or native login item captures no profile (`electron/main.js:38-42`, `:240-242`) → fresh process resolves paths again → storage load/default creation (`scripts/local-config-store.mjs:32-49`) → ordinary selection/RPC (`scripts/studio-server.mjs:185-208`, `:298-326`). Transient parent environment is not a durable restart contract.
- Evidence of plan gap: SPEC:156-160 explicitly supports custom, partially overlapping and disjoint profiles; SPEC:168-176, 210, 216 requires handoff/startup/backout but checks one launcher and bytes/opt-out without specifying the profile descriptor carried by it. WF:59, 63 requires startup contracts but omits this invariant. This is separate from F16's competing startup authorities.
- Minimal correction: runtime exposes a nonsecret immutable startup descriptor for the resolved config/secrets paths, host and port; lifecycle's launcher/update/backout restores that same descriptor, or explicitly rejects autostart for unsupported custom profiles before changing preferences. Verify the restarted process's resolved identities, not only launcher presence. Add split-directory/custom-path/space-containing-path fixtures and a default-profile sentinel asserting zero writes there; never embed key values in launcher arguments or receipts.
