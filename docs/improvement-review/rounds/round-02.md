## New findings, frozen before inherited-review comparison

### R2-M1 — Major: the browser trust contract does not prohibit framing Studio

Consequence: where a browser admits loopback framing, a foreign page can overlay Studio and induce real first-party clicks that publish Presence or change startup/settings; its valid bootstrap token and own-origin API calls bypass foreign-request rejection.
Evidence: `IMPROVEMENT-SPEC.md:132` protects Host/Origin/token and `:136` specifies CSP scripts/images/navigation, but neither decides `frame-ancestors`/embedding. `scripts/studio-server.mjs:735` serves the document without an embedding restriction; `scripts/discord-presence-studio.html:2863` and `:3257` own Show/startup mutations. Electron main-frame IPC checks do not protect the CLI browser UI.
Trace: foreign iframe → actual Studio document/transport → real click handler → valid token/Origin → committed command → RPC/startup side effect → first-party success despite misleading parent presentation.
Minimal correction: W1 must send `Content-Security-Policy: frame-ancestors 'none'` on Studio document responses, with `X-Frame-Options: DENY` fallback; require direct top-level navigation. Add a G5 foreign-parent framing fixture that proves blocked rendering and zero mutations while direct Studio works.
This is a missing design rule, not a demonstrated browser exploit: browser-specific admission of a loopback frame remains an isolated proof, and cannot substitute for the embedding policy.

### R2-M2 — Major: GIF cancellation/pagination lacks upstream and retained-result bounds

Consequence: rapid queries or several Studio tabs can continue consuming the configured provider quota after UI cancellation; long browsing retains thousands of image nodes/decoded media and can undermine the promised responsive editor.
Evidence: `IMPROVEMENT-SPEC.md:71` promises latest-query/cancellation/pagination, while `:190` bounds discovery but gives no GIF admission/retention policy. Renderer abort/sequence checks at `scripts/discord-presence-studio.html:2713`, `:2726`, `:2742` discard obsolete results; the server's `:844` search handler does not propagate disconnect cancellation. `scripts/giphy-search.mjs:141` creates its own ten-second signal, and `:232` starts every cache miss before caching at `:239`; `maxEntries` bounds completed cache entries only. Renderer `:2644`, `:2669`, `:2692` appends media on successive pages without a retained-page limit.
Trace: typing/scroll/tab → renderer cancellation/new request → per-process search/cache → overlapping provider fetches or appended thumbnails → timeout/cache only after work → latest result visible but abandoned work and old media remain.
Minimal correction: assign W1/security plus UX one explicit bounded GIF contract: coalesce identical in-flight searches, cap provider concurrency/queued work, cancel upstream when its last requester disconnects, and cap retained thumbnails/pages with a visible continuation action. Preserve provider errors/429 and release admission slots in `finally`.
Meaningful tests: deferred fake fetches for cancellation, repeated keys, many distinct keys and multiple clients; assert the actual upstream in-flight cap and cleanup, then exercise enough page appends to prove the retained-node cap. G6 measures the chosen bounds; it must not choose the ownership/admission policy later.
Pure isolated source probe: imported only `createCachedGiphySearch`, used a synthetic key and deferred fake fetch, then submitted two identical queries and one different query (one caller already aborted). With `maxEntries: 1`, all **3 provider fetches** started before resolution; no network/server/Discord/helper ran. This confirms completed-cache limits do not establish in-flight coalescing or cancellation.
